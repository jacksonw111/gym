# 普瑞健身 CloudBase 数据访问层重写设计

## 1. 目标

本次只重写云函数读取和写入数据库的方式，并配套调整后台与小程序的请求组织。业务规则、页面功能和现有数据继续保留。

完成后需要达到以下结果：

- 不使用前端缓存；每次查询都以数据库当前数据为准。
- 任一接口只查询完成该操作所需的集合和记录，不再预先加载全部集合。
- 写操作只锁定并修改相关记录，不再使用覆盖全库的全局事务。
- 后台按当前页面加载数据，不再进入系统时一次下载所有管理数据。
- 小程序每个页面使用一个面向该页面的查询接口，避免同一页面重复获取身份和业务数据。
- 旧课包即使缺少 `status` 字段，也能正常显示并进行上架或下架。
- 核心业务的并发安全、权限判断和课时流水规则保持不变。

## 2. 已确认的问题

当前云函数在处理每个请求前都会依次读取 11 个集合。一次后台刷新会并发调用三个接口，因此至少产生约 33 次集合查询；数据超过单页限制后还会继续分页读取。

每次写操作还会在一个全局事务中再次读取全部集合，比较所有记录后逐条写回。该方式会同时造成查询慢、事务时间长和不同业务相互争抢同一把锁。

线上现有 4 条课包记录均没有 `status` 字段。后台把缺失状态显示为“已下架”，但云函数在修改时拒绝没有该字段的记录，因此出现“资源不支持状态变更”。

## 3. 新的数据访问方式

### 3.1 查询

为每个集合提供小而明确的查询方法，例如：

- 按记录 ID 查询。
- 按会员、教练、日期、状态查询。
- 按一组关联 ID 批量查询。
- 使用数据库的计数、排序、限制和分页能力。

业务接口组合这些查询方法，只获取需要的数据。例如课包上架只按 ID 查询并更新一条课包；查看某位教练某天的课程表只查询该教练、当天排班和当天预约。

所有查询在服务端完成权限过滤。客户端不直接访问核心业务集合。

### 3.2 写入与事务

删除当前全局 `system_locks/domain` 锁和“读取全库后比较写回”的事务模式。

需要保证多个数据同时变化的操作继续使用数据库事务，但事务只读取和修改相关记录：

- 预约：目标会员课包、目标时段、冲突预约和新预约。
- 取消：目标预约、对应会员课包和课时流水。
- 完成课程：目标预约、对应会员课包和课时流水。
- 申诉退课：目标申诉、目标预约、对应会员课包和课时流水。
- 管理员调整课时：目标会员课包和课时流水。

教练资料、课包资料、用户资料等单记录修改直接按文档 ID 更新，不进入多集合事务。

### 3.3 并发与重复提交

同一教练、日期和开始时间使用稳定的占用记录 ID，预约事务通过该记录保证同一时段只能成功一次。取消后删除或释放占用记录。

会改变课时的请求继续携带唯一请求标识。服务端在事务中检查对应流水或结果，重复提交返回原结果，不再次扣减或退回课时。

## 4. 接口组织

### 4.1 小程序

不增加任何 60 秒或其他时长的前端数据缓存。

每个页面改为一次查询获得渲染所需的数据和当前身份：

- 会员首页：身份、会员概览、上架课包、可用教练和下一节课程。
- 会员课程：身份和当前会员的课程列表。
- 教练详情：身份、会员可用课包、目标教练资料和指定日期课程表。
- 教练工作台：身份、教练资料、当天课程和待处理事项。
- 教练排班：身份、教练资料和指定日期排班。
- 我的：身份和当前用户资料。

页面切换和手动刷新会真实查询数据库。页面内部多个组件不会各自重复发起相同查询。

### 4.2 网页后台

后台不再通过一个全量数据对象支持所有页面，也不使用前端数据缓存。

- 概览页查询统计数字和近期记录。
- 教练、会员、课包、预约、申诉页面各自调用独立列表接口。
- 列表由数据库完成筛选、排序和分页。
- 新增、编辑、上下架或处理申诉成功后，只重新查询当前页面。
- 页面切换时查询目标页面的最新数据，不提前读取未打开页面的数据。

管理员登录会话仍按当前安全方式验证，但每个业务请求只读取会话、管理员和该操作需要的业务记录。

## 5. 课包状态兼容

课包状态只有 `published` 和 `unpublished` 两种值。

- 读取旧记录时，缺少或非法状态统一视为 `unpublished`，避免旧商品意外售卖。
- 上架或下架操作直接设置目标记录的状态，不要求旧记录预先存在该字段。
- 新增课包始终写入明确状态。
- 部署时执行一次幂等迁移，把现有缺少状态的课包补为 `unpublished`；重复执行不会改变已有合法状态。

## 6. 数据库索引

根据实际查询增加组合索引，至少覆盖：

- 预约：`memberId + startAt`、`coachId + startAt`、`status + endAt`。
- 排班：`coachId + date`。
- 会员课包：`memberId + status`、`coachId + status`。
- 申诉：`memberId + createdAt`、`status + createdAt`。
- 订单：`memberId + createdAt`、`status + createdAt`。
- 管理员会话：`tokenHash + expiresAt`。

只有代码实际使用到的查询才创建索引，不预先增加无用索引。

## 7. 迁移顺序

1. 为新的精准查询和事务行为补充自动测试，并记录当前查询次数作为基线。
2. 建立新的 CloudBase 数据访问接口，先迁移课包和只读页面接口。
3. 迁移预约、取消、完成、排班、申诉和课时调整等事务接口。
4. 将后台改为按页面查询，将小程序改为每页单次查询。
5. 执行课包状态数据迁移并部署必要索引。
6. 删除全库加载、全局锁和全量比较写回代码。
7. 运行全部单元测试、类型检查和生产构建，再部署云函数与后台。

迁移过程中保留现有接口响应字段，直到对应页面完成切换，避免前后端在同一次部署中出现版本错配。

## 8. 验证标准

- 课包上架最多读取目标课包及管理员身份相关记录，并只更新目标课包。
- 查看一位教练一天的课程表不读取订单、申诉、流水或无关教练数据。
- 后台打开课包页不读取预约、订单、排班和课时流水集合。
- 小程序会员首页只发起一个业务查询；教练详情切换日期只查询新日期所需数据。
- 两个会员并发预约同一时段时只有一个成功。
- 重复取消、完成、申诉退课和课时调整不会重复改变课时。
- 现有缺少状态的课包可以成功上架和下架。
- 所有现有业务测试继续通过，并新增数据库查询次数断言。
- 后台和小程序生产构建成功；部署后的云函数日志中不再出现每次请求读取全部集合或全局事务争抢。

## 9. 不包含的内容

- 不增加前端缓存、离线数据或过期时间策略。
- 不改变预约、取消、完成、反馈、申诉和课时扣减的产品规则。
- 不重做页面视觉设计。
- 不更换 CloudBase，也不迁移现有业务数据到其他云服务。
